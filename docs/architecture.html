00

Overview

Two people use this system: an admin, who uploads a school's curriculum material and manages access, and a student, who asks for solutions, notes, sample papers, or ad-hoc answers grounded in that material. Everything both of them do passes through the same three layers.

01

Data layer — Postgres + pgvector

One Supabase Postgres database, playing two roles at once.

Rather than a separate vector database, the RAG corpus lives in the same Postgres instance as everything else, using the pgvector extension. chunks.embedding is a vector(768) column, filled by Gemini's gemini-embedding-001 truncated to 768 dimensions via its outputDimensionality parameter, searched with an IVFFlat cosine-similarity index.

  • schools / grades / subjects — the taxonomy every student and every document is tagged against.
  • students — one row per Supabase Auth user: role, active flag, school/grade/subject assignment, token_quota.
  • llm_settings — admin-editable provider + model per task type.
  • documents / chunks — the RAG corpus. Each chunk carries its taxonomy tags, its text, its embedding, and image_path — the storage path of the scanned page it came from.
  • token_usage — one row per LLM call, normalized regardless of provider.
  • generated_documents — a record of every PDF a student has generated.

Two RPCs do the work application code shouldn't reimplement: match_chunks() runs a taxonomy-filtered cosine search, and student_monthly_usage() sums a student's token_usage for the current calendar month. Row-Level Security enforces the boundaries directly in Postgres — a student can only see their own profile and usage; the knowledge base and taxonomy are readable by any active student but writable only by admins, via an is_admin() helper function.

Files

  • supabase/migrations/0001_init.sql — full schema, RPCs, RLS policies.
  • supabase/migrations/0002_chunk_images.sql — adds chunks.image_path and updates match_chunks().

02

Authentication & access control

Supabase Auth for credentials, a students row for everything app-specific.

Sign-up creates the Supabase Auth user and an app-level students row in the same step — but the row starts active: false. Nobody can self-grant access; an admin has to flip the switch at /admin/students first.

src/proxy.ts (Next.js 16 renamed middleware.ts to proxy.ts) runs on every request and enforces three gates in order: no session → /login; session but inactive → /pending; active non-admin hitting /admin/* → /dashboard. The actual gate logic lives in lib/supabase/middleware.ts so it can also refresh the session cookie on the way through.

Files

  • src/proxy.ts — entry point Next.js invokes on every request.
  • src/lib/supabase/middleware.ts — session refresh + the three redirect rules.
  • src/lib/actions/auth.ts — signIn / signUp / signOut server actions.
  • src/lib/auth.ts — getCurrentStudent() / requireAdmin(), used by every server component and API route that needs to know who's asking.

03

LLM abstraction layer

One function the rest of the app calls; the provider behind it is a database row.

Every generation call — student-facing or ingestion-time — goes through generateCompletion() in src/lib/llm/index.ts. It never talks to a vendor SDK directly: it looks up which provider + model handles this taskType from the llm_settings table, then hands off to that provider's adapter.

Three adapters — providers/google.ts, anthropic.ts, openai.ts — each wrap one vendor's SDK behind the same interface, and each normalizes its response into an identical shape: {'{'} text, usage: {'{'}inputTokens, outputTokens, totalTokens{'}'} {'}'}. That normalization is what lets the quota system (section 7) work the same way no matter which vendor actually served a request.

Google is the default and does double duty: it's the primary completion provider and the only embeddings provider — embed() always calls the Google adapter, since Anthropic has no embeddings API and the pgvector column's dimensionality is fixed to Gemini's embedding model.

Config, not code. Changing which provider/model serves solution generation is a row update in llm_settings via /admin/llm-settings — no redeploy, and every downstream system (quota, PDF export) keeps working unchanged.

Files

  • src/lib/llm/index.ts — generateCompletion() / embed(), the entry point.
  • src/lib/llm/config.ts — reads llm_settings, 30s in-process cache.
  • src/lib/llm/types.ts — the shared request/response shapes every adapter implements.
  • src/lib/llm/providers/google.ts — Gemini adapter (completions + embeddings + search grounding).
  • src/lib/llm/providers/anthropic.ts — Claude adapter (completions only).
  • src/lib/llm/providers/openai.ts — OpenAI-compatible adapter (completions + embeddings).
  • src/lib/llm/usage.ts — writes a token_usage row after every call.

04

Ingestion pipeline

Admin uploads scanned pages; the pipeline turns them into searchable, taggable knowledge.

An admin uploads a chapter's worth of scanned/photographed pages at /admin/documents, tagged once with school, grade, subject, and source type — there's no per-page manual work. ingestDocument() then does four things to every page, in order:

  1. Store the image. The raw page is uploaded to sources/{'{'}documentId{'}'}/page-{'{'}n{'}'}, before anything else happens to it.
  2. Transcribe it. extractPageText() sends the page to Gemini's vision input directly — no dedicated OCR vendor.
  3. Chunk it. chunkPageText() splits the transcription on heading/section boundaries, capped around 1,500 characters per chunk.
  4. Embed and index it. Each chunk is embedded and inserted into chunks, carrying the page's taxonomy tags and its image_path — linking the text back to the page it came from.

That last link is deliberate: OCR text alone loses an anatomy diagram or a map — it can describe what's on the page, not show it. By keeping every page's image and linking it to the chunks extracted from it, retrieval can hand the original image back alongside the text, automatically, for any subject — see section 5.

Files

  • src/lib/ingestion/ingest.ts — orchestrates the four steps above per page.
  • src/lib/ingestion/extract.ts — the vision transcription call.
  • src/lib/ingestion/chunk.ts — section-aware text chunker.
  • src/app/api/admin/documents/route.ts — upload endpoint; GET lists documents and their status.

05

RAG retrieval core

One retrieval function, reused by all four generation workflows.

retrieveContext(query, scope) embeds the incoming prompt, then calls the match_chunks RPC — a taxonomy-filtered cosine search scoped to the student's own school, grade, and subject, returning the top 8 matches. If the best match's similarity falls below a threshold (or there are no matches at all), the result is flagged coverageLow — the one signal allowed to unlock web search grounding, which keeps the "RAG first, search only if needed" policy enforced in code rather than just in the prompt.

loadSourceImages(chunks) takes the matched chunks, de-duplicates their image_paths (several chunks often share one page), caps the result at four images, and downloads them — for two consumers at once: the LLM call itself, and the PDF/UI layer that cites them later.

Files

  • src/lib/rag/retrieve.ts — retrieveContext(), loadSourceImages(), formatContext().

06

Generation pipeline

Four routes, one shared spine — they differ only in task type.

Solutions, notes, sample papers, and ad-hoc answers are four thin route files that all call the same runGeneration() function with a different taskType. That function is the whole pipeline end to end:

src/lib/generation/handler.ts wraps that pipeline into a single POST-handler factory; each route file is one line calling it with its task type. The route also owns what the pipeline doesn't: rendering the PDF, uploading it, inserting a generated_documents row, and minting a signed download URL for the response.

Files

  • src/lib/generation/pipeline.ts — runGeneration(), the sequence above.
  • src/lib/generation/prompts.ts — the RAG-first system instructions, one per task type.
  • src/lib/generation/handler.ts — shared route factory: PDF render, upload, respond.
  • src/app/api/generate/{'{'}solution,notes,sample-paper,ad-hoc{'}'}/route.ts — four one-line routes.

07

Quota enforcement

A per-student monthly token ceiling, checked before every generation call.

checkQuota(studentId) sums the student's current-month usage via the student_monthly_usage RPC and compares it against students.token_quota. runGeneration() calls this first, before spending anything on retrieval or an LLM call — a student over quota gets turned away at the door, not after the expensive part has already run.

Being over quota throws a typed QuotaExceededError that the route handler catches and turns into an HTTP 429 carrying the actual usage numbers, so the client can render "247k / 250k tokens used" rather than a generic failure. Usage itself is written after every completion call, using the normalized {'{'}inputTokens, outputTokens, totalTokens{'}'} object every LLM adapter returns — the quota system doesn't know or care which vendor served the request.

Files

  • src/lib/quota.ts — checkQuota(), QuotaExceededError.
  • src/lib/llm/usage.ts — writes the token_usage row.
  • src/app/api/me/route.ts — profile + live quota status, polled by the dashboard's usage bar.

08

PDF export

One renderer, shared by all four generation types, serving only signed URLs.

renderGenerationPdf() is a single @react-pdf/renderer template with a light markdown-ish formatter — headings, bullets, **bold** — and a per-task-type label in the header. Every generation route calls the same function; nothing about the PDF layout is duplicated per task type.

Where a cited source has an image_path, the PDF embeds that image inline next to its citation — a diagram survives all the way from the scanned page to the exported PDF, not just the on-screen answer. The finished file is uploaded to Cloudflare R2 and never served directly: getSignedUrl() mints a one-hour link, so the storage bucket itself stays private — and R2's zero egress fees matter here specifically, since a popular generated PDF gets re-downloaded, not just stored once.

Files

  • src/lib/pdf/render.tsx — the shared template + inline image embedding.
  • src/lib/storage.ts — uploadPdf, uploadSourceFile, downloadFile, getSignedUrl.
  • src/app/api/documents/[id]/download/route.ts — re-signs a URL after the original expires.

Admin panel

Four working areas, each a thin page over a matching API route.

AreaDoesRoute
StudentsGrant/revoke access, set role, school/grade/subject, quota/api/admin/students
TaxonomyAdd schools, grades, subjects/api/admin/taxonomy
Knowledge baseUpload scanned pages → triggers ingestion/api/admin/documents

Every admin route calls requireAdmin() before touching the service-role client — RLS is the backstop in Postgres, not the only gate; the route itself refuses a non-admin before a query is ever issued.

10

Student dashboard

Generate, see the answer and its sources, download the PDF, revisit past ones.

/dashboard is a four-tab form — one per generation type — over a live quota bar. A result shows the answer text, the cited sources (with their images inline, where the source chunk carried one), and a PDF download link. /dashboard/documents lists everything the student has generated before, re-signing a fresh download URL on demand since the original one expires after an hour.

Files

  • src/app/dashboard/page.tsx — the generation form + result view.
  • src/app/dashboard/documents/page.tsx — generation history.
  • src/app/api/documents/route.ts — lists the current student's own generated documents.
